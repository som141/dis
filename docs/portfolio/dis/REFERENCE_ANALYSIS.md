# 공개 이력서·포트폴리오 사례 분석과 DIS 작성 기준

확인일: **2026-10-27**

서로 다른 개발자 3명의 공개 이력서와 프로젝트 설명을 직접 읽었다. 추천 목록이나 디자인만 보지 않고, 경험을 어떤 순서로 설명하는지, 주장 뒤에 어떤 사례를 붙이는지, 해결하지 못한 부분을 어떻게 드러내는지 비교했다.

선정 기준은 **빠르게 이해할 수 있는 요약, 실제 불편에서 출발한 이야기, 본인이 한 판단, 확인할 수 있는 결과, 경험의 범위에 맞는 표현**이다. 유명한 개발자의 문서라는 이유로 모든 표현을 좋은 예시로 받아들이지는 않았다. 아래 원문은 문장 복사의 대상이 아니라 구성과 설명 방식의 참고 자료다.

| 황준일 · 소개와 단국대 시간표 개인 프로젝트 | 짧은 서비스 요약 뒤에 재학 중 느꼈던 불편, 한 학교로 대상을 좁힌 이유, 별도 서버를 보류한 선택을 설명한다. 끝에는 홍보 시점의 시행착오와 테스트를 남기지 못한 아쉬움도 적는다. | 기술 소개보다 서비스가 필요했던 이유가 먼저 나온다. 선택하지 않은 방법과 실제 사용 과정의 아쉬움까지 읽을 수 있어 개인 프로젝트의 판단 과정이 보인다. | DIS를 만든 계기와 실제 이용 장면을 먼저 설명한다. 필요한 기술만 그 판단에 연결하고, 실제로 확인하지 못한 결과도 명확히 남긴다. |

## 2. 이동욱: 성향을 구체적인 행동으로 설명하기

- 주요 확인 범위: `Summary`와 경력별 담당 업무. 특히 README 24~34행의 문서화·운영 문제 대응 설명.

### 참고할 대목

이 문서는 문서화를 좋아한다는 설명 다음에 실제 사례를 붙인다. 도구의 라이선스가 있어도 환경 설정과 사용 안내가 없어 기존 도구를 계속 쓰던 상황에서, 먼저 사용해 보고 정리해 공유한 경험이다. 배포 이력이 정리되지 않은 프로젝트를 맡았을 때 실행·배포 방법을 README에 남긴 경험도 이어진다.

읽는 사람은 이 사례를 통해 작성자의 성향뿐 아니라 **불편을 발견한 배경, 본인이 한 행동, 다음 작업자를 위해 남긴 것**을 이해할 수 있다. DIS도 단순히 문서를 작성했다고 적기보다, 로그 확인이나 배포 방법을 다시 찾아야 했던 구체적인 불편과 연결할 수 있을 때 더 설득력이 있다.

### 이번 글에 적용할 점과 한계

- 이력서 소개에는 책임감·문제 해결 능력 같은 단어를 반복하지 않고, 해당 태도가 드러난 행동을 짧게 붙인다.
- 운영 사례는 사용자에게 나타난 증상을 먼저 쓰고, 확인 과정과 변경 내용을 이어 쓴다.
- 원문은 2016년의 이력서여서 기술 목록과 소개가 길다. 현재 DIS 이력서에는 필요한 경험만 압축한다.
- 원문의 회사 규모·트래픽·근무 기간은 해당 작성자의 이력이다. DIS의 사용자 수나 처리량을 설명하는 근거로 사용하지 않는다.

## 3. 남정호: 요약과 상세 설명을 나누고 경험의 범위를 밝히기

### 확인한 원문

- [상세 프로젝트 이야기 STORY](https://github.com/samchon/resume/blob/6b25156b3723a4f4b93029ffd02b0daaa56cca9e/STORY.md)

- 주요 확인 범위: README의 요약→상세 연결, STORY의 `Fake Iamport Server`·`Backend`, `Unitech` 프로젝트 설명.

### 참고할 대목

README는 짧은 소개와 프로젝트 목록을 보여 주고 각 항목을 상세 문서로 연결한다. 상세 문서는 프로젝트의 목적과 선택을 더 길게 설명한다. 이 구분은 이력서를 빠르게 읽는 사람과 프로젝트를 깊게 확인하려는 사람을 모두 고려한다.

상세 문서에는 하드웨어를 다시 만들기 어려운 제약 때문에 소프트웨어로 해결하려 했지만 행정상의 이유로 중단된 프로젝트도 등장한다. 기여 범위와 중단 사실을 함께 표시해, 시도한 해결책과 최종 결과가 같은 뜻이 아님을 드러낸다.

또한 외부 결제 서비스를 흉내 낸 테스트 서버는 기술 이름만 소개하지 않고, 수동 화면 테스트에 의존하지 않고 자동으로 확인하기 위해 만들었다는 목적을 설명한다. DIS의 주입기나 가상 응답 테스트도 **실제 외부 서비스를 매번 호출하기 어려워 내부 처리 흐름을 확인하기 위한 수단**으로 설명하는 데 참고할 수 있다. 다만 가상 응답과 실제 서비스가 동일하게 동작한다는 결론까지 따라 쓰지는 않는다.

### 이번 글에 적용할 점과 한계

- 이력서에서는 DIS의 목적·역할·챌린지 3개만 빠르게 보여 주고, 상세 포트폴리오에서 조사와 판단을 풀어 쓴다.
- 개발을 마쳤다는 말, 가상 테스트가 통과했다는 말, 실제로 이용해 결과를 확인했다는 말을 나누어 쓴다.
- 현재 Maple 프로토타입처럼 실제 인증 확인이 남은 기능은 앞으로의 작업이나 별도 실험으로 표시한다.
- 원문에 있는 배수 성능이나 무장애 표현은 작성자의 자기 보고이며 이 조사에서 독립 검증하지 않았다. DIS에 같은 수식어나 숫자를 가져오지 않는다.
- 강한 자기평가와 긴 기술 설명까지 모방하지 않는다. 이번 글은 개인 프로젝트의 실제 운영 경험에 맞는 길이와 표현을 사용한다.

- 주요 확인 범위: 프로젝트 글의 짧은 요약, 시작 계기·범위·서버 보류 판단, 홍보·후기.

### 참고할 대목

시간표 서비스 글은 재학 시절 시간표 공개를 기다리고, 기존 서비스에 반영될 때까지 다시 기다렸던 경험에서 시작한다. 이어 모든 대학이 아니라 자신의 모교 한 곳을 대상으로 정한 이유를 설명한다. 기술을 쓰고 싶어서 서비스를 붙인 인상보다, 해결할 불편과 범위를 먼저 정한 과정이 드러난다.

별도 API 서버가 있으면 더 많은 기능을 제공할 수 있지만 우선 보류했다는 선택도 나온다. 현재 필요한 수준에서 무엇을 만들고 무엇을 미뤘는지 알 수 있다. 마지막에는 시간표 공개 전에 홍보해 효과적이지 않았던 일, 공개 뒤 다시 홍보한 일, 테스트 코드를 작성하지 못한 아쉬움까지 남긴다.

DIS에도 이 순서가 적합하다. 처음 만든 계기는 **사용자가 직접 말한 내용이나 당시 기록에서 확인한 사실**로 시작하고, 이후 실제 사용 중 나타난 불편과 바꾼 일을 연결한다. 예상한 대로 되지 않았던 부분을 모두 성과로 포장할 필요가 없다.

### 이번 글에 적용할 점과 한계

- 일반 소개를 읽으면 봇이 무엇을 하는지 이해되고, 더 읽으면 어떤 불편 때문에 변경했는지 알 수 있게 쓴다.
- 기술 선택은 가능한 기능 목록보다, 당시 조건에서 왜 그 정도의 해결책을 골랐는지 설명한다.
- 사용자에게 확인받은 결과와 운영하면서 남은 불편을 함께 적는다.
- 원문은 구현 튜토리얼을 포함한 긴 프로젝트 글이다. 제출용 포트폴리오에는 코드와 라이브러리 설명을 그대로 옮기지 않는다.
- 홍보 반응이나 작성자의 다른 회사 경험을 DIS의 사용자 반응·성과로 대입하지 않는다.

## 5. DIS 원고의 검토 기준

| 검토 항목 | 확인할 질문 | 수정이 필요한 신호 |
| --- | --- | --- |
| 시작 계기 | 처음 만든 이유에 당시 기록이나 사용자 설명이 있는가? | 확인되지 않은 친구·커뮤니티·사업 목적을 그럴듯하게 추가함 |
| 독자 이해 | 처음 읽는 사람이 봇의 기능과 사용 장면을 설명할 수 있는가? | 첫 문단부터 도구 이름과 구조 설명이 나열됨 |
| 실제 문제 | 사용자가 겪은 불편이나 운영 중 확인한 상황으로 시작하는가? | 규모 확대·성능 향상 같은 추상적인 문제만 등장함 |
| 조사와 판단 | 어떤 기록을 보고 무엇을 판단했는지 이어지는가? | 결과만 있고 그 해결책을 선택한 이유가 없음 |
| 결과 | 바꾼 뒤 무엇을 확인했는지, 근거와 범위가 있는가? | 측정하지 않은 비율·처리량·복구 시간·무중단을 단정함 |
| 테스트 범위 | 실제 Discord 사용, 내부 주입 테스트, 가상 응답을 구분하는가? | 모의 실험 수치를 실제 이용량이나 외부 서비스 성능으로 씀 |
| 진행 상태 | 운영 중인 기능과 프로토타입·계획을 구분하는가? | 미검증 인증이나 미구현 알림을 완성된 서비스로 소개함 |
| 문장과 분량 | 이력서는 짧게, 상세 판단은 포트폴리오에서 읽을 수 있는가? | 같은 기술 목록과 자기평가가 여러 문서에서 반복됨 |

이번 작성에서는 **이력서의 짧은 요약 → 챌린지 3개 → 상세 운영 사례 → 확인된 결과와 남은 한계**로 나누어, 한 프로젝트를 읽는 깊이에 따라 이해할 수 있도록 한다.

외부 사례의 경력·규모·성과는 해당 작성자의 공개 설명이다. 이 문서는 그 사실을 독립 검증하거나 채용 성과를 보장하는 평가가 아니다. DIS의 사실 확인은 DIS의 대화·코드·커밋·실행 기록을 근거로 별도로 수행한다.
