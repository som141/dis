이 검토는 제출용 이력서와 구분한 작성 근거다. 공개 README의 자기소개, 프로젝트 설명, 연결된 저장소의 파일을 확인했다. 학적·성적 증명서를 확인하거나 다른 프로젝트를 실제 실행한 결과는 아니다. 연락처는 복제하지 않았다.

## 검토 기준

1. **무엇을 했는지 읽히는가:** 성격에 대한 자기평가보다 실제로 만든 기능, 확인한 문제, 취한 행동이 앞에 오는지 본다.
2. **현재 구현과 맞는가:** 과거의 계획을 이미 완료한 일 또는 아직 남은 일로 구분한다.
3. **본인의 역할을 설명할 수 있는가:** 개인 프로젝트, 팀 과제, 도구 활용 범위를 구분한다. 팀원의 일이나 다른 기업의 성과를 본인 성과로 쓰지 않는다.
4. **근거를 따라갈 수 있는가:** 프로젝트 링크가 열리고, 설명한 기능을 README·코드·실험 기록에서 찾을 수 있는지 본다.
5. **성과의 범위가 분명한가:** 기능 구현, 실제 운영 관측, 가상 테스트, 계획을 구분한다. 확인하지 않은 수치나 업무 경험을 추가하지 않는다.

## DIS 제작 동기로 확인되는 범위

기존 이력서에는 생활 속에서 필요를 느낀 기능을 직접 구현한다는 설명에 DIS가 예로 연결돼 있다. 프로젝트 설명에는 Java·JDA·LavaPlayer로 봇을 만들고 GCP에 올려 사용했다고 적혀 있다.

따라서 다음 정도는 기존 기록에 근거해 쓸 수 있다.

> 일상에서 필요한 기능을 직접 만들어 사용해 보고 싶어 Discord 음악 봇을 개발했습니다. Java로 음악 재생 기능을 만들고 클라우드에 배포해 사용하면서, 사용 중 생긴 문제를 고치는 프로젝트로 이어갔습니다.

유료 음악 봇을 대체하려 했는지, 몇 명이 사용했는지, 친구들의 요청이 계기였는지는 이 문서만으로 확인되지 않는다. 별도 사용자 설명이나 운영 자료가 없다면 추가하지 않는다. 현재 서버의 제공자를 이력서의 과거 GCP 배포 경험만으로 단정하지도 않는다.

이번 작성 중에는 사용자가 2026-10-27에 **2024년 Discord 봇들이 동작하지 않던 경험이 계기였으며, 현재 지인 약 30명과 사용 중**이라고 직접 확인했다. 개정본은 이 추가 진술을 반영했다. 약 30명은 동접·월간 이용자 통계로 바꾸지 않는다. 외부 사건 맥락은 [ORIGIN_CONTEXT.md](ORIGIN_CONTEXT.md), 주장별 범위는 [EVIDENCE.md](EVIDENCE.md)에 정리했다.

## 개정본에 권하는 비중

DIS는 실제 사용과 운영 중 문제 해결을 설명할 수 있는 대표 프로젝트로 배치한다. ERP·블로그·날씨 앱 중 지원 직무와 설명 가능한 경험에 맞는 보조 프로젝트를 고르고, 짧은 학습 실습은 한두 줄로 정리한다. 상세 기술 설명은 포트폴리오로 연결하고 이력서에는 사용자에게 생긴 문제, 본인의 행동, 확인된 결과를 남기는 편이 좋다.

공개 이력서에 있던 연락처는 이 검토에 다시 싣지 않았다. 최신 학력·성적·실사용 범위 등 본인 확인이 필요한 정보는 채용 문서의 완성도를 높이기 위해 남긴 확인 항목이며, 실제 경험 대신 임의로 채울 수 있는 빈칸이 아니다.
