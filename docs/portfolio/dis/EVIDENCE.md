# DIS 이력서·포트폴리오 주장 검증

확인일: **2026-10-27** · 기준 코드: [`32df09c84365726d5c110472738f913bdef25fae`](https://github.com/som141/dis/tree/32df09c84365726d5c110472738f913bdef25fae).

이 문서는 이력서와 포트폴리오의 문장을 어떤 기록으로 뒷받침할 수 있는지 정리한다. 저장소의 소스·테스트·커밋, 공개 GitHub Actions 실행 결과, 작성자와의 이 대화를 확인했다. 이번 검증에서 운영 서버를 변경하거나 GitHub workflow를 실행하지 않았다. 테스트 코드가 존재한다는 것과 지금 그 테스트를 실행해 통과했다는 것은 구분한다.

## 1. 근거의 종류와 표현 범위

| 구분 | 확인한 것 | 본문에서 쓸 수 있는 범위 |
| --- | --- | --- |
| 사용자 실사용 확인 | 이 대화에서 증상·로그·수정 후 사용 결과를 공유 | 작성자가 겪은 경험으로 기술. 누구나 열람 가능한 공개 장애 보고서라고 표현하지 않음 |
| 공개 실행 결과 | Actions의 커밋·실행 단계·성공/실패 메타데이터 | 해당 실행이 성공/실패했다는 사실. 단계 결과만으로 세부 원인·서비스 음질·이용자 수를 추정하지 않음 |
| 당시 재현 기록 | 저장소에 남긴 원인·재현·대응 문서 | 문서에 기록된 문제와 조치를 인용. 이번에 원본 로그를 다시 읽은 것처럼 쓰지 않음 |
| 코드·회귀 검사 | 실제 구현과 특정 상황을 검증하는 테스트 | 구현·검사 범위 설명. 대규모 운영에서 손실이 없었다는 보장으로 확대하지 않음 |
| 미확인 | 출처가 없거나 원본 로그를 읽을 수 없는 세부 주장 | 수치와 원인을 만들어 채우지 않음 |

단, 사용자 확인이 담긴 이 대화에는 공개 열람 URL이 없다. 공개적으로 확인 가능한 것은 수정 커밋·현재 코드·회귀 검사이며, 작성자의 청취 확인까지 독립적인 공개 로그로 검증했다고 표현하지 않는다. 장기간·모든 곡에서 재발하지 않았다는 근거도 없다.

이 사례는 **“구조를 점검하며 발견한 응답 순서 문제를 개선하고 회귀 테스트로 확인했다”**로 쓰는 것이 정확하다. 특정 일자의 실제 운영 장애 건수나 응답 누락 비율은 확인되지 않았다. “운영에서 발생한 수천 건의 메시지 유실을 없앴다” 같은 사고 규모·성과 수치는 붙이지 않는다.

권장 문장: **“작업이 빨리 끝나더라도 결과를 돌려줄 사용자를 놓치지 않도록, 응답 정보를 먼저 저장한 뒤 작업을 보내는 순서로 정리하고 테스트로 확인했습니다.”**

## 5. 챌린지 3 — 코드는 바뀌지 않았는데 외부 라이브러리를 받지 못해 빌드가 막힘

이 사례는 아래 세 가지 근거를 합쳐 설명한다. **당시 재현 문서**, **동일 버전을 유지한 수정 코드**, **수정 전후의 공개 CI 결과**를 서로 구분한다.

| 문제는 문서 변경 후 실행한 CI에서도 드러났다 | 문서 개선 [커밋 `cca3f87`](https://github.com/som141/dis/commit/cca3f87e8f5ee4860bc75aaa1b935a693e0d3906), [실패 run 39722112212](https://github.com/som141/dis/actions/runs/39722112212) | **공개 실행 결과 확인.** `Test and build with Gradle` 단계 실패. 문서 수정이 음악 코드 오류를 만들었다는 뜻은 아님 |
| 라이브러리 설명 파일을 받아야 하는 URL에서 HTML이 돌아왔다 | [gradle/README.md](../../../gradle/README.md)의 5~9행 | **당시 재현 기록 확인.** 2026-10-22 POM URL이 XML 대신 폴더 목록 HTML을 반환했고 `Already seen doctype`로 의존성 해석이 실패했다고 기록 |
| 기능 버전 변경 없이 공식 배포 파일로 공급 경로를 바꿨다 | [커밋 `32df09c`](https://github.com/som141/dis/commit/32df09c84365726d5c110472738f913bdef25fae), [youtube-source-releases.gradle](../../../gradle/youtube-source-releases.gradle#L3)의 3~27행 | **구현 확인.** 기존 1.18.2의 두 모듈만 공식 GitHub release에서 선택. 다른 의존성은 기존 공급 설정 사용 |

| 기존 런타임 의존성을 보존했다 | 같은 Gradle 파일의 30~53행, gradle README의 18~26행 | **구현·출처 기록 확인.** 원본 release commit의 빌드 파일을 근거로 필요한 의존성 metadata 유지 |

권장 문장: **“외부 저장소가 정상적인 라이브러리 설명 파일을 돌려주지 않아 빌드가 막힌 문제를 조사했습니다. 기능 버전을 무작정 바꾸지 않고, 같은 버전의 공식 배포 파일을 사용하며 파일 검증을 추가했고 이후 빌드와 배포가 통과한 것을 확인했습니다.”**

확인 한계: 실패 run의 로그는 이번 점검에서 GitHub의 별도 로그 다운로드 도메인 접근이 거절되어 본문을 다시 읽지 못했다. 남아 있는 annotation은 exit code 1뿐이다. 따라서 **POM→HTML 원인은 저장소의 재현 기록에 근거하며, 이번에 원본 실패 로그를 직접 열어 같은 오류를 재확인했다고 쓰지 않는다.** 성공/실패 단계 메타데이터는 공개 API로 확인했다. 공식 파일 사용과 해시 검사가 공급 문제 전체를 영구 해결한다는 보장도 아니다.

## 8. 최종 문장 점검 기준

1. 각 챌린지는 사용자에게 보인 불편이나 작업을 막은 상황부터 설명한다.
2. 조사한 사실, 바꾼 동작, 확인한 결과가 서로 연결돼 있는지 본다.
3. 음악 정상화는 작성자의 실사용 확인이며, 응답 순서 개선은 코드·회귀 검사이고, 빌드 복구는 재현 기록·수정 코드·공개 CI 결과라는 차이를 유지한다.
4. 공개 저장소에서 볼 수 없는 대화·로그를 공개 링크로 검증한 것처럼 표현하지 않는다.
5. 수치·원인·개인적 제작 동기가 없으면 추정으로 채우지 않는다. 확보한 기록의 범위만큼 구체적으로 쓴다.
